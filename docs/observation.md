# 工作期间持续观察与理解

## 目标与状态

用户明确要求覆盖整个工作期间，及时理解实际工作。Codex 负责理解与判断，Luna 提供观察工具、短期上下文与长期知识；不另建模型推理内核。

已实现并测试下文的工作切片工具；实际是否采集中以 `luna observe status` 为准。后续方案中的自动触发 Codex、浏览器和编辑器专门接口仍待实现，当前对话未验证可以自动接收外部事件。

## 已实现的工作切片工具

```sh
uv run luna observe start
uv run luna observe status
uv run luna observe stop
uv run luna observe report
```

macOS 专用；需要 Swift 编译器、屏幕录制和辅助功能权限。本机 2026-11-11 已验证实际截图、窗口文本和 OCR 成功。Python 启动脱离终端会话的采集进程；并非独立 Agent，无模型调用。launchd 注册在本机测试中失败，因此当前版本不依赖 launchd，不提供登录自启或进程崩溃自动恢复。

默认约每 2 秒读取前台应用、窗口和受限长度的辅助功能文本，约每 4 秒采样各活动显示器截图并执行 OCR；耗时操作会延长间隔，并非逐帧录像或完整消息存档。锁屏时跳过窗口和截图采集；记录权限状态、采集错误、事件时间与完成时间。没有专门的浏览器 URL、后台消息或 VS Code 扩展接入，只采集实际可见画面和可读取的前台窗口信息。

原始材料位于 `.local/observation/<本地时间标识>/`，由 `current.json` 指向最新切片：

- `events.jsonl`：UTF-8 事件、窗口文本、OCR 和错误记录；时间字段为带时区的 UTC。
- `frames/`：按采样编号保存各显示器 JPEG。
- `state.json`：PID、计数、错误、心跳及状态；`status` 额外检查进程存活和心跳年龄。
- `timeline.md`：`report` 导出的可读时间线，供 Codex 结合截图理解；不会自动随采集更新。
- `stop`：停止请求标记；当前采样结束后写入停止状态。

单次切片最多 8 小时或约 4 GiB 截图，到限后停止并保留原因；原始内容不自动上传、不自动删除。不要仅根据 `recording` 判断健康，还要检查进程存活、心跳、错误及权限。暂停此次采集使用 `stop`，恢复使用 `start` 创建新切片。

用户说工作切片结束时，先请求 `stop`，确认状态为 `stopped`，再导出时间线并读取事件和必要截图；区分观察事实与推断，指出采样盲区。当前切片的本地起点标记优先于测试记录；不要把测试过程当成用户工作。后台实时保存事实已实现，持续触发 Codex 语义理解尚未实现。

## 首次切片验证后的分析方法

2026-11-11 实际切片已验证后台采集、停止与事后还原；本次事件平均间隔约 2.09 秒，最大约 2.82 秒，无截图或 OCR 报错。这些指标只证明该次采集的运行情况，不代表语义完整或实时理解已实现。

- 先按正式起点过滤测试与等待阶段，再按前台应用/窗口变化定位关键片段，去重文本后读取必要截图；完整分析保存在切片本地目录，仓库只沉淀通用方法。
- 记录“观察时间”和画面内“消息/日志原始时间”的区别；可见的历史对话不能当成刚发生的新事件。截图中的背景窗口和标签页不代表用户正在操作它们。
- Telegram 的辅助功能文本可能很少，需结合 OCR 与截图；OCR 内容涉及代码、地址或数字时回看原图，不直接据其改配置。
- 终端退出码 130 结合 `^C` / SIGINT 判断为中断退出；只有对应错误证据才能推断异常原因。屏幕没有变化也不能单独证明用户空闲。
- 空闲时间应读取任意输入事件的间隔（`CGEventType(rawValue: UInt32.max)`）；`.null` 是空事件类型，会产生误导性的大数。首次切片的该字段已发现无效，不用于分析，传感器已修正，下次启动生效。

## 最小数据路径

工作变化 → 本机采集与去重 → 本地事件缓冲 → 触发 Codex 读取增量 → 更新当前工作理解 → 按授权协助。

采集器只获取、规整和缓冲事实，不负责语义推理。全工作期间覆盖不等于每帧调用模型；持续采集变化，按重要事件和短时间合并触发理解。采集延迟、等待处理时间与模型处理时间分别记录。

## 先接入的信号

| 信号 | 用途与边界 |
| --- | --- |
| 前台应用、窗口、切换时间、锁屏及空闲状态 | 知道当前工作表面和覆盖是否中断；窗口标题本身不足以判断工作意图 |
| 当前浏览器页面 URL/标题与按需页面内容 | 关联 PR、Linear 任务、文档和站点；具体浏览器接入需验证 |
| VS Code 当前项目、文件与必要的诊断信息 | 定位代码工作；优先通过结构化接口获取，不能假设所有编辑器状态都已开放 |
| 按变化采样的截图和可访问性文本 | 补足 TG、弹窗、终端等 UI 上下文；实际读取能力与系统权限逐项验证 |
| GitHub、Linear 等平台的事件或查询结果 | 补充当前页面之外的任务状态，不能直接等同于用户当前意图 |

首个原型先打通前台应用/窗口与必要视觉上下文，再根据漏掉的实际信息补浏览器或编辑器适配。仅靠应用名和窗口标题不能宣称已实现工作理解。

## 理解结果

保持简短的当前工作记录：正在做什么、关联项目/任务、近期关键变化、可能的阻塞、证据及时间、哪些是推测、观察缺口。切换应用不自动代表切换任务；长时间停留也不自动代表遇到困难。

区分采集正常、等待理解、理解完成与覆盖缺口。锁屏、休眠、权限失效、采集器停止或模型不可用应显式留下缺口，恢复后标识补处理的数据，不能称为实时理解。

## 接入 Codex

- MCP 可提供“当前状态”“某时间后的增量”“按需截图”等读取工具；提供工具本身不等于自动唤醒 Agent。
- 官方 App Server 提供会话与 turn 的程序化接口，是事件触发 Codex 的候选接入方式。它仍使用 Codex；无需自行实现模型调用和推理循环。
- 验证本机版本、登录、工具权限、目标会话与串行处理方式。不能假设可直接向当前桌面对话注入事件或继承它的所有连接器。
- 先做一条工作事件触发一次 Codex 理解的实验，再确定全天接入。不预建复杂调度系统；若当前环境只能定时运行，明确它只达到周期理解。

官方资料（2026-11-11 查阅，具体本机能力未验证）：[MCP](https://developers.openai.com/codex/extend/mcp)、[App Server](https://developers.openai.com/codex/app-server)。

## 开销与数据管理

建议先以本机工作时段的变化触发加短窗口合并进行实验；窗口稳定时降低截图频率，明确新事件优先，避免旧事件无限积压。具体时延、资源和存储上限由原型测量后确定。

原始事件、窗口内容和截图放在 Git 忽略的 `.local/`，配置短期保留与清理，不随自动 push 上传。只将提炼后的必要经验写入文档；不采集全局键盘输入或剪贴板作为默认数据源。提供暂停、恢复、状态、排除应用和删除本地记录的简单入口。

## 第一阶段验收

选择一段真实工作过程，至少经历浏览器、编辑器、聊天之间的切换；Codex 应能根据证据持续更新工作理解，用户不必逐次解释。比较实际工作与推断，核对延迟、漏采、错误关联、资源开销和恢复行为。先对照验证准确度，再扩大观察范围和主动处理能力。

优先级与运行边界来自用户需求；信号选择、接入方式和验收步骤为本次建议，尚未实现或实测。
