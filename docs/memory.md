# 知识沉淀与检索

## 内容归属

| 内容 | 位置 |
| --- | --- |
| 高频、跨任务的协作规则 | 根目录 `AGENTS.md` |
| 用户确认的稳定偏好与背景 | `docs/context.md` |
| 项目操作规范、架构和通用流程 | `docs/` 固定路径文档 |
| 已验证经验、排障方法、重要决策和研究结论 | `docs/knowledge/` |
| 知识附件 | `docs/assets/` |
| 任务目标、临时笔记、执行进度、交付物 | `workspaces/<任务名>/` |
| 本地缓存、执行日志、未来任务数据库 | `.local/` |

## 每次任务的默认动作

1. 开始前检索现有知识。先找最新知识索引，再按主题、关键词、状态与验证时间选择页面；只加载与任务相关的内容。
2. 执行中记录对结论有用的来源、关键命令和验证结果，不复制完整聊天或所有工具输出。
3. 结束前评估：是否有以后能复用的方法、重要决策、明确偏好或已经验证的失败原因？有则主动沉淀；没有则无需制造日志或知识条目。
4. 优先维护已有主题。规则要短、可执行；细节留在文档。修复受影响的索引、链接和状态。
5. 在交付回复中简要说明重要的知识更新，让用户能发现和纠正记忆。

## 长期知识格式

`knowledge/` 和 `assets/` 均平铺。文件名使用有意义的点分主题与时间版本，例如：

```text
workflow.github.review.v2026-11-11-220442.md
workflow.github.review.example.v2026-11-11-220442.png
```

版本、元数据的时间统一使用 Asia/Shanghai，必须取实际写入或验证时间，不复用示例时间。知识页最小模板：

```yaml
---
title: 主题
status: current
created_at: YYYY-MM-DD HH:MM:SS
updated_at: YYYY-MM-DD HH:MM:SS
last_verified_at: YYYY-MM-DD HH:MM:SS
freshness: stable
version: vYYYY-MM-DD-HHMMSS
related: []
assets: []
---
```

正文包含摘要、可执行结论、证据和开放问题；必要时增加适用范围、验证方法和版本变化。`freshness` 可为 `stable`、`time-sensitive`、`volatile`、`historical`。未经核验的内容使用 `status: needs-verification`，`last_verified_at: null`，不要编造验证记录。

语义变化优先生成新版本，旧页标为 `superseded`，新旧页分别用 `supersedes` / `superseded_by` 指向对应文件；保留历史。仅格式、错字、链接修复可原地更新。编辑时间与事实验证时间分别维护，格式整理不刷新验证时间。

每次知识维护同时更新带时间版本的 `kb.index` 与 `kb.log` 页面及入口引用。相关主题才维护，不自动进行全库重命名或删除。索引与日志同样遵守版本关系。

## 质量与隐私

- 来源可以是用户明确陈述、仓库文件、已执行命令或外部链接；结论应标注适用条件，易变事实使用前重新核验。
- 新信息与旧结论冲突时记录差异和证据；无法判断则保留为开放问题。
- 不存储 token、cookie、密码、完整聊天和无必要的个人信息；错误输出和截图也应先检查敏感内容。
- Git 管理长期知识；工作区默认不入 Git。将工作区结论迁入文档时先做必要删减。
- 不依赖模型跨会话自行记住；记录文件路径与恢复入口，供后续会话重新读取。
