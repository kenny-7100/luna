# 自动化与外部集成

## 当前能力边界

本项目已建立本地知识、工具和任务组织基础，并提供按需启动的 macOS 工作切片采集进程，详见 [工作观察方案](observation.md)。它可在对话回复结束后继续保存本地事实，不调用模型。自动触发 Codex 理解、消息监听与外部账号集成尚未实现。

## 目标与下一步建议

用户已明确希望在当前电脑上持续运行，低打扰地主动发现并解决遗漏的问题，并接受提供广泛访问权限。访问范围决定能够观察什么；实际动作仍需结合既有授权、对象与影响判断，不必为已明确的持续授权重复确认。

Codex 是 Agent 主体，Luna 提供知识、工具和可恢复的任务上下文。此前建议另建调用模型的 Python worker 偏离用户目标，已撤回；不因此引入常驻代理、模型 SDK 或独立推理循环。

初期验收重点是：电脑唤醒或进程重启后恢复，重复问题不重复处理，能定位证据、在授权范围内执行并验证结果，未解决事项能恢复跟进。提供启动、暂停、状态和停止入口；普通处理留日志或汇总，需要用户决策或确有时效性时才通知。休眠、断网和电脑关机期间不承诺实时工作。

下一步应先核实当前 Codex 环境可用的持续执行、任务触发与恢复机制，再以最少配置让 Codex 使用本项目开展真实工作。必要时只补充轻量触发或状态工具；具体产品能力核实前不承诺会话外自动继续执行。目前没有安装常驻任务。

## 接入顺序

先选择一个实际高频需求，逐步完成“读取 → 理解 → 草稿或执行 → 结果回写 → 经验沉淀”。每接入一个平台，记录连接方式、账号或项目范围、授权动作、验证方法与失败恢复方式。

| 平台 | 候选用途 | 待明确内容 |
| --- | --- | --- |
| Telegram | 接收任务、通知、回复 | Bot 还是用户会话，允许访问的聊天，代回复授权 |
| Linear | 需求整理、状态推进、任务发现 | 工作空间、团队、项目、允许更新的字段 |
| GitHub | 代码变更、PR、CI、Issue 跟进 | 仓库范围、认证、创建或合并权限 |
| VS Code / Codex | Codex 作为执行主体，读取知识、调用工具、恢复任务 | 当前环境支持的触发和持续协作方式 |
| Chrome / 部署网站 | 查看状态、验证交付、观察异常 | 网站、环境、登录方式和允许操作 |

优先由 Codex 使用已有连接器、CLI 或官方 API；缺少确定性的工具能力时再在项目中补充脚本。不同执行环境的工具与权限须实际核实，不假设可以直接继承。

## 主动发现

第一阶段在相关任务执行过程中发现改进机会，把“证据、意义、建议动作、预期收益”记录到任务中，避免无来源的建议。发现机会本身不授予对外行动权限。

后续可按用户选择的范围巡检 PR/CI、Linear 阻塞或网站状态。持续巡检需实现明确的频率、去重、限流、通知渠道和停止方式，并在接入前明确覆盖范围。

## 持续运行的交付条件

具体需求出现后，优先使用 Codex 已有机制并仅补充必要工具。至少验证以下实际行为：

- 任务能持久化，重启后恢复，失败有限重试，重复事件不会重复发送或修改。
- 凭据由环境或系统密钥管理提供；日志保留动作与错误，过滤敏感数据。
- 可查看任务状态与执行记录，有明确启动、停止和禁用方式。
- 外部动作有授权范围；明确授权可持续使用，范围外的动作先形成草稿或计划。

通知和代回复属于对外消息，需要用户明确授权；用户明确要求某次发送或给定持续范围后，按该授权执行。发布、部署、合并、删除同样遵循具体任务授权，不因“个人分身”的目标而默认拥有所有操作权限。
